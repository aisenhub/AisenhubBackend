# ARCHITECTURE_BLOCKER AB-001

Blocker ID: AB-001  
Task: P1-T013 — Complete P1 contract and security matrix  
Architecture Reference: `docs/implementation/phases/01-identity-application-session.md` P1-T013; `docs/implementation/phases/03-admin-foundation.md` P3-T002  
Status: OPEN

## Problem

P1-T013 requires verification of `GET /v1/admin/session`, including normal-user 403, disabled membership, and AAL/MFA cases. The approved implementation plan assigns the Admin Session implementation to P3-T002, which depends on P1 and is the first task in the Admin Foundation phase. The current P1 code therefore has no Admin Session route to exercise.

## Evidence

- P1-T013 acceptance requires every P1 route to have required cases and a normal user to receive 403 from Admin Session.
- P3-T002 explicitly owns `GET /v1/admin/session`, Admin authorization middleware, and its handler tests.
- The current `platform-api` routes are session exchange/read/delete, profile, and public application reads; no Admin Session handler exists.

## Why Agent Cannot Safely Decide

Implementing a second Admin Session path in P1 would duplicate the P3-owned backend boundary and could create incompatible session or AAL semantics. Marking P1-T013 complete would falsely claim an unimplemented security boundary has passed.

## Minimal Proposed Change

Choose one approved planning correction: move P3-T002 into P1 before the P1 gate, or revise P1-T013 acceptance to defer Admin Session verification to P3-T002 while retaining the P1 contract-only coverage.

## Affected Tasks

- P1-T013
- P1-T014
- P3-T002

## Current Workaround

All implemented P1 routes have a passing security/contract matrix in `docs/implementation/reports/P1-T013-security-matrix.md`. P1-T013 remains `in_progress`; no Admin API authorization claim is made.
